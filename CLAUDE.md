# ZYNEX — Project Rules

> Also read `AGENTS.md` — this Next.js version has breaking API changes vs. older
> training data; it points to the bundled docs in `node_modules/next/dist/docs/`.
> It's regenerated by `next dev`; keep it committed.

ZYNEX is an AI-powered product studio (UAE-based, serving globally). This repo is the
official marketing site + admin dashboard. AI designs/builds websites, portals, web apps,
mobile apps, dashboards and AI agents for clients, shipping in days not months.

Target clients: small businesses, startups, enterprises. English only.

## Tech Stack (do not deviate)

- Next.js (latest, App Router) + TypeScript
- Tailwind CSS + shadcn/ui (install components via shadcn MCP, never hand-roll)
- Motion (motion.dev / Framer Motion successor) for UI animation
- Three.js via React Three Fiber + @react-three/drei for 3D scenes
- Lenis for smooth scrolling
- Supabase (Postgres + Auth + Storage) — leads, blog, portfolio, chat logs
- Vercel AI SDK for the chatbot, provider-agnostic (swap via env vars)
- Zod for form/schema validation
- Deploy target: Vercel

## Tools to use while building

## Brand & Design Tokens

Dark, futuristic, premium — not a generic SaaS template. Glassmorphism panels, engineering-grid backdrop, subtle
film grain, glowing borders, animated gradients used sparingly (accents/CTAs, not full
backgrounds).

"ZYNEX AI theme" taken from the user's Fleet Bridge proposal artifact — it supersedes the
original blue/lime proposal):

| `--surface` / `--surface-2` / `--surface-3` | `#0B0D14` / `#11141D` / `#181C28` | panels/cards (glass over these) |
| `--foreground` | `#E8ECF5` | primary text |

| `--border` / `--line-2` | `#1C2130` / `#2C3348` | hairlines / stronger hairlines |
| `--brand` (= `--primary`) | `#5EF2FF` | electric cyan — primary CTA, links, glow; dark text (`--primary-foreground` `#031418`) on top |
| `--brand-2` | `#A78BFA` | violet — secondary accent |
| `--brand-3` | `#F0ABFC` | pink — gradient end / tertiary |

| `--destructive` / `--success` | `#FF6B7A` / `#6EE7B7` | errors / success |

Radii: `--radius-sm: 8px`, `--radius-md: 14px`, `--radius-lg: 24px`.
Shadows: soft ambient shadow + colored glow shadow variant using `--brand` at low opacity.

**Typography** (Google Fonts):
- Display: **Unbounded** (headings — wide, so use the fluid `.h-xl`/`.h-lg`/`.h-md` classes, not fixed `text-4xl`)
- Body: **Geist**; mono labels/buttons/eyebrows: **Geist Mono**

**Motion language:**
- Hero: letter-cascade headline over the site-wide cosmic nebula background, swapping noun, build-console terminal
- Cursor dot + ring, card spotlight (`.fx-card`) and 3D tilt (`.fx-tilt`), button
  ripple, scroll-progress bar — all delegated from `components/fx/fx-provider.tsx`
- Scroll-driven reveals (Motion `useScroll`/`whileInView`)
- Magnetic buttons, text scramble/split-text headings on hero + section titles
- Animated gradient accents on borders/CTAs, page transitions between routes

**3D/perf rules:**
- Lazy-load all 3D (dynamic import, `ssr: false`), pause render loop when canvas is
  off-screen (IntersectionObserver), cap `pixelRatio` at 2
- Static fallback (poster image or CSS gradient) on low-power devices and when
  `prefers-reduced-motion` is set
- Targets: Lighthouse Performance 85+, Accessibility/SEO 95+
- Mobile-first, fully responsive

## Workflow

1. CLAUDE.md (this file) first — done.
2. Short build plan → wait for explicit approval before writing code — approved.
3. Build order, commit after each stage:
   a. setup + design system
   b. layout, nav, footer
   c. home page with 3D hero
   d. remaining marketing pages
   e. quote builder + booking + WhatsApp
   f. chatbot
   g. admin dashboard
   h. SEO + performance pass
4. Subagents: at most 2 concurrent, only for clearly separable work (e.g. admin
   dashboard vs. Playwright visual QA). Everything else stays in the main session.
5. After each stage: Playwright visual check (1440px + 390px) + `npm run build`; fix all
   errors/type issues before moving to the next stage.
6. `.env.example` lists every var with a comment. No secrets in code or commits.
7. Final deliverable includes a README: setup, Supabase connection, chatbot provider
   config, Vercel deploy steps.

## Notes / deviations

- The hero has no dedicated 3D/canvas background any more: earlier iterations (R3F
  sphere, "Particle Drift", then the Originkit "Accretion Disc") were all removed; the
  hero sits on the site-wide cosmic nebula. `@react-three/fiber` / `@react-three/drei`
  stay installed per the stack requirement for any future 3D scene, unused today.
- Stage (e) — Contact page (`app/contact/`): quote builder is hand-rolled with
  `react-hook-form` + `zod` rather than shadcn's `form.tsx` — the shadcn CLI
  silently no-ops on `add form` for the `base-nova` (Base UI) style/registry
  combo in this project, so `FormField`/`FormItem` wrappers were never
  available; not worth chasing since the direct `Controller`/`register` API
  is one layer thinner anyway. Also note: Base UI's `Checkbox`/`RadioGroup`
  items render as `<span role="radio|checkbox">`, not a native labelable
  input, so wrapping them in a plain `<label>` does NOT forward click-to-toggle
  the way it would for a real `<input>` — every checkbox/radio option card in
  `quote-builder.tsx` has an explicit `onClick`/`toggle` on the `<label>` to
  compensate. Booking uses a plain `<iframe src="{CAL_LINK}?embed=true&theme=dark">`
  (`components/sections/booking.tsx`) instead of `@calcom/embed-react` — no new
  dependency, same result for a single embedded event type.
- Stage (f) — chatbot (`app/api/chat/route.ts`, `lib/ai/`,
  `components/chat/chat-widget.tsx`): built against AI SDK v7 / `@ai-sdk/react`
  v4's UI-message-stream protocol (`useChat` + `DefaultChatTransport` +
  `streamText(...).toUIMessageStreamResponse()`), noticeably different API
  from older AI SDK docs (`convertToModelMessages` is now async, for one). The
  route checks `isAiConfigured()` first and returns a 503 with a friendly
  message when `AI_PROVIDER`/`AI_MODEL`/`AI_API_KEY` aren't set (they aren't
  yet — deferred per the user) instead of throwing; the widget surfaces that
  message in the chat pane rather than erroring out. Rate limiting is a
  best-effort in-memory per-IP counter (`lib/ai/rate-limit.ts`) — fine for a
  single instance, swap for a durable store if this ever runs multi-instance.
  Conversation logging to `chat_sessions`/`chat_messages` uses the service-role
  client and is best-effort (wrapped in try/catch) so a logging hiccup never
  breaks the chat reply.
- Stage (g) — admin dashboard (`app/admin/`): follows the `(protected)` route
  group from the target folder structure above — `app/admin/layout.tsx` is a
  bare noindex shell, `app/admin/login/page.tsx` is a standalone magic-link
  form (no dashboard chrome), and everything under `app/admin/(protected)/`
  gets the real nav + sign-out via its own nested layout. `proxy.ts` (written
  in stage (a)) already gated `/admin/*` on `user.email === ADMIN_EMAIL`, and
  `components/layout/marketing-chrome.tsx` hides the marketing nav/footer/
  WhatsApp button/chatbot on `/admin/*` (same pathname-prefix pattern as
  `page-background.tsx`). CRUD (leads status/notes, case studies, blog posts)
  uses plain HTML forms + Server Actions against the cookie-based Supabase
  client — no service-role client needed, since `is_admin()` RLS policies
  already grant the admin full read/write on every table once signed in.
  Image fields (`cover_image_url`, `gallery_image_urls`, `og_image_url`) are
  plain URL text inputs for now, not a Storage upload UI — a reasonable v1
  scope cut; wire up Supabase Storage + an upload widget later if needed.
  Verified: proxy correctly redirects an unauthenticated visitor to
  `/admin/login`; a real magic-link email round-tripped through Supabase Auth
  successfully; RLS was exercised directly in SQL (`set local role
  authenticated; set local request.jwt.claims ...`) confirming
  `zidane.k967@gmail.com` passes `is_admin()` and can read/write every admin
  table while an arbitrary other email cannot. Could not click through the
  actual magic-link into the authenticated dashboard screens in this
  session — the browser tool declined to navigate to the `supabase.co` auth
  domain — so the admin page UIs themselves are compile-verified

- Stage (h) — SEO + perf pass: `app/sitemap.ts` and `app/robots.ts` use the
  Next.js file-convention (not static XML/txt files), pulling live case-study
  and blog slugs from Supabase; `/admin` and `/api` are disallowed.

  `next/og`'s `ImageResponse` (no real brand asset existed yet) — the root
  layout's `openGraph.images`/`twitter.images` point at it, and since every
  marketing page's own `metadata` export only sets `title`/`description`
  (never its own `openGraph` object), Next's shallow per-key metadata merge
  means they all inherit that image automatically; `blog/[slug]` and
  `portfolio/[slug]` already override `openGraph.images` with the real
  content's `cover_image_url` when set, so this doesn't clobber those. Added

  chrome tinting. 3D lazy-loading / `prefers-reduced-motion` handling and
  `next/image`/`next/font` usage were already in place from earlier stages —
  this pass didn't need to touch them.
